## 1. 技术设计约束

技术方案必须服从 Product Definition 与 Functional Requirements，不得通过实现便利改变以下产品语义：

- Project 是一级核心对象，Workspace 与 Project 不重复建模；
- 一个 Project 对应一个本地目录；
- App Session 与真实 CLI Conversation Session 保持 1:1；
- Session 不是 Task，UI 不引入 Run 作为主要用户概念；
- 一个 Session 固定一个 CLI；
- 多 Session 可以并行；
- Project Knowledge 与最终 View 展示必须分离；
- 客户端不自研 Agent Profile Framework，优先复用 CLI 原生能力。


## 2. V1 推荐技术栈

V1 采用 **Electron + React + TypeScript** 作为跨平台桌面客户端技术栈。该选择服务于本产品的本地项目管理、CLI 进程管理、内嵌 Browser、Terminal 和流式 Conversation 要求。

### 技术栈基线

| 层级 | 选型 | 主要职责 |
|---|---|---|
| Desktop Shell | Electron | 窗口、菜单、系统集成、主进程和渲染进程协调 |
| UI | React + TypeScript | Conversation、Project Tabs、Project View 和 Context Panel |
| 构建工具 | electron-vite | 主进程、Preload 与 Renderer 的开发和构建 |
| 包管理 | pnpm | 依赖安装、Workspace 管理和可重复构建 |
| UI 状态 | Zustand | Project、Session、布局和工具面板状态 |
| 本地运行时 | Node.js + TypeScript | CLI Adapter、Session Manager、Process Manager、文件和 Git 操作 |
| 本地持久化 | SQLite | Project、Session 映射、UI 状态、未读标记和本地索引 |
| Project Knowledge | JSON / Markdown + Schema 校验 | 结构化知识存储，并与 View Definition 分离 |
| Terminal | xterm.js + node-pty | 终端渲染、PTY 创建、输入输出和窗口大小调整 |
| Files / Diff | Monaco Editor（按需加载）+ Git CLI | 文件查看和 Agent 变更审核 |
| Browser Preview | Electron WebContentsView | Localhost 页面预览和受控网页嵌入 |
| 打包发布 | electron-builder | macOS、Windows、Linux 安装包、签名和发布 |
| 验证 | Vitest + Playwright | Adapter、状态机、本地持久化和桌面关键流程验证 |

### 分层边界

客户端分为四个逻辑层：

1. **Renderer UI**：只负责界面呈现和用户交互，不直接访问文件系统、Shell 或凭据；
2. **Preload Bridge**：通过最小化、类型化的 IPC API 暴露受控能力；
3. **Application Services**：负责 Project、Session、View、Knowledge 和工具状态；
4. **Runtime Services**：负责 CLI 子进程、PTY、文件系统、Git 和 Browser 实例。

CLI Agent、用户 Terminal 和 Browser Preview 必须使用独立的进程或渲染上下文。任何由 AI 生成的 HTML / JavaScript 都不得直接获得 Node.js、文件系统或完整 IPC 权限。

Electron 是 V1 的确认选型。Tauri 2 不作为 V1 主线框架；后续只有在安装包体积或资源占用成为明确约束时，才重新进行替代方案评估。

### 首发平台

- V1 首发 **macOS**，于 2026-10-08 确认。
- 首轮开发前校验环境为 macOS 15.6 / Apple Silicon（arm64）；这不是最低系统版本或完整兼容性承诺。
- 最低 macOS 版本、Intel（x64）支持范围及签名 / 公证流程仍需通过打包验证确定。
- Windows / Linux 保留跨平台架构边界，暂不列入首发验收范围。

### 开发前 CLI 校验

2026-10-08 已在 macOS arm64 完成真实 CLI 验证，见 [CLI Integration Preflight](<06. CLI Integration Preflight.md>)。Codex 使用 App Server stdio 协议；Claude Code 使用官方 Agent SDK Streaming Input 驱动已安装 CLI。创建、流式输出、同一原生 Session 恢复、授权 / 问题作答及并行运行均已验证。

Codex 0.161.0 的 `turn/interrupt` 用于中断当前回合，Unified Exec 会保留后台命令。先前三次“收到 `interrupted` 后测试子进程仍存活”的观察保留，但不能仅凭该行为判定 Codex 进程终止缺陷。补充源码核对与真实调用已验证 `thread/backgroundTerminals/clean` 和 `thread/backgroundTerminals/terminate`：测试进程退出，同一 Runtime 中另一 Thread 继续执行，原 Thread 保留上下文并可继续对话。正常 Stop 应优先使用原生进程清理；终止独立 Runtime 后恢复同一 Session 作为清理失败或接口不可用时的兜底路径，详见校验报告第 4、5 节。

首阶段仍建议每个活动 Session 使用独立 Runtime，以隔离崩溃和 Runtime 终止兜底。原生清理在共享 Runtime 中的 Thread 隔离已验证，独立 Runtime 并非正常 Stop 的接口前提；若采用共享 Runtime，须证明兜底也不会影响其他 Session（FR-SESSION-003）。

CLI Adapter 需要关联用户主动取消与原生终态：本次 Claude 主动取消返回 `error_during_execution`，不能仅凭该类型标为 Error。具体映射及剩余校验见校验报告第 5、6 节。

## 3. CLI 原生能力复用原则

客户端应优先复用 Codex CLI、Claude Code CLI 本身已有的：

- Session；
- Model；
- Agent；
- Skill；
- Rule；
- Prompt；
- Context Reference；
- File Reference；
- Directory Reference。

客户端职责是：

- 提供 GUI；
- 管理多个 Session；
- 提供 Project Context；
- 展示状态；
- 展示 Project Knowledge；
- 提供工程辅助工具。

V1 不重新实现一套自研 Agent Framework。

## 4. User Terminal 与 Agent Runtime 隔离

用户 Terminal 与 CLI Agent 自身使用的 Runtime / PTY 必须逻辑分离。

原因：

- 防止 cwd 互相影响；
- 防止 Agent 修改用户 Shell 状态；
- 防止 Agent 意外终止用户进程；
- 保持运行状态可预测。

### Codex Stop 实现约束

以下约束用于实现输入区的 Stop（FR-INPUT-001）和多 Session 隔离（FR-SESSION-003），不新增 UI 状态或独立 Run / Task 概念。

1. Stop 时暂停该 Session 的新任务提交，记录用户取消意图，发送 `turn/interrupt` 并处理对应回合终态；不能收到 `interrupted` 就宣告资源清理完成。
2. 优先复用原生后台命令接口。初始化时开启 `capabilities.experimentalApi: true`；这些接口为实验性能力，应锁定支持的 CLI 版本与生成的协议类型，并处理接口不可用的情况。
3. 停止本轮命令时，关联 `threadId`、`turnId`、`itemId` 与 App Server `processId`，使用 `thread/backgroundTerminals/terminate` 精确终止目标。`processId` 是 App Server 内部编号，不是系统 PID。本轮归属映射和保留先前后台服务的行为仍需正式 Adapter 验证。
4. `thread/backgroundTerminals/clean` 清理该 Thread 全部后台命令，包括先前回合启动的服务；仅在清理范围明确包含这些命令时使用。不得用清理整个 Thread 的操作隐式替代本轮命令终止。
5. Stop 完成须同时确认回合结束和目标命令退出。`clean` 的空响应仅表示请求已提交，后台列表清空也不能单独证明系统进程已退出；Process Manager 需获取退出证据，并为清理设定有限等待时间。
6. 清理超时、失败或接口不可用时，可终止该 Session 的独立 Runtime，确认所属进程清理后，再以原 `thread.id`、cwd 和配置恢复。该兜底可能停止同一 Session 先前启动的后台命令，不能承诺保留这些服务；范围与恢复行为须纳入 Adapter 校验。
7. 任何清理或恢复都不得终止其他 Session、Project 或用户 Terminal。清理失败时不得并行启动新旧 Runtime；恢复失败时不得静默创建新 Session，也不得自动重跑已取消的命令。

## 6. 非功能需求

### 性能

- Project 切换应保持即时响应；
- 大量历史 Session 不应导致左侧列表明显卡顿；
- 多 CLI Session 并行不得阻塞主 UI；
- Agent 输出必须支持流式展示。

---

### 稳定性

单个 Session CLI 进程失败：

不得导致：

- Application 崩溃；
- 其他 Session 中断；
- 其他 Project 中断。

---

### 本地性

V1 以本地开发工程为核心。

客户端必须正确处理：

- 本地文件读写；
- 本地 Shell；
- CLI Process；
- Project Directory；
- Localhost Preview。

---

### 可扩展性

CLI Integration 不应硬编码为只有两个永久实现。

架构上需为未来新增其他 CLI Agent 留出 Adapter 能力。

但 V1 实际交付范围：

- Codex CLI；
- Claude Code CLI。

## 7. 技术设计阶段验证与待决事项

以下内容需要在技术方案和跨平台原型阶段验证或确定：

1. Project Knowledge 实际存储格式；
2. Project Knowledge 是否存储在 Project 内部隐藏目录；
3. AI Generated View 的 HTML 渲染及安全沙箱方案；
4. Codex App Server 与 Claude Code Session 的恢复、取消和错误恢复行为（Codex 原生清理与 Runtime 兜底均已验证；本轮进程归属、后台服务保留、实验接口兼容和清理失败恢复仍需实现与校验）；
5. CLI 输出统一事件模型（校验报告已给出映射输入，正式类型与 Adapter 尚未实现）；
6. Needs Input / Completed / Error 状态的 CLI Adapter 映射方式（授权与问题等待已验证；需处理主动取消差异及 UI 状态机）；
7. 多 Agent 同时修改相同文件时的冲突检测方案；
8. Git / Worktree 是否进入 V1.1；
9. macOS 最低版本、CPU 架构覆盖及后续 Windows / Linux 支持范围（首发 macOS 已确认）；
10. Project View Context 如何注入不同 CLI；
11. Project View 数据自动更新时机及权限边界；
12. Electron 原生依赖在各平台和 CPU 架构上的构建与签名流程；
13. 非 Git 目录的 Diff 基线，以及每轮修改文件的识别方式（FR-TOOL-002）。
