## 1. 已确认方向

用户通过对话或模板创建可由宿主加载的 Web 页面插件，复用本地 Project、导航和现有 CLI Session。2026-11-11 用户明确调整推进顺序：先设计系统的插件架构，建设通用插件机制，后续再以五图等业务验证承载能力。同日用户明确确认本方案，授权 agent team 以 DeepSeek Harness 原则推进插件机制开发及对照验收，并要求满足功能时尽量避免整体引入复杂机制。本文确认的是分阶段方案，后续范围与候选事项仍按 §2.2 的时点处理；实施不等于人工产品验收。

Harness 作为插件机制与 AI 创建流程的参考，不另设方向可行性验证阶段，也不以前置五图交互原型阻塞架构工作。实现过程仍需检查本产品的加载、通信、生命周期与恢复。五图布局、出图工具、内容位置、产物绑定和版本管理属于后续业务方案，不能成为每个插件必须实现的基础协议。已确定事项见 §2.1，候选交互与后续范围见 §2.2，技术事项见 §2.3。

### 2.2 未确定事项

保留原问题编号，拆出的细节使用 `.1` 等后缀。以下区分分阶段评审的候选交互和后续范围；“暂采纳”是设计依据，不是最终设计确认。

#### 候选交互，按所属阶段评审

下表保留 2026-11-10 暂采纳的交互方案。按 2026-11-11 的顺序调整，创建、编辑、预览和加载反馈随插件机制设计与实现评审；图片选择、生成反馈、产物恢复及生成中的删除行为留到业务阶段。不再要求先完成五图原型。暂采纳不等于最终设计确认，候选方案可在评审时调整。

| 编号 | 问题 | 暂采纳方案 | 原因与主要取舍 | 评审定稿时点 |
|---|---|---|---|---|
| WB-Q3.1 | 创建、编辑、预览和添加至项目的入口如何组织 | 宿主提供“添加工作台”，进入后选对话创建或模板；草稿预览后再添加。“编辑工作台”放在实例操作中，预览后应用 | 能分清设计草稿与正在使用的实例，减少误改成果；创建与编辑需要分别呈现状态 | 插件机制阶段，随可运行交互评审 |
| WB-Q4.1 | 生成与结构编辑如何切换和提示 | 日常对话留在内容模式；明确进入编辑时展示草稿状态，应用前说明位置增删对现有内容的影响 | 避免出图时误改定义；增加一次明确的模式切换 | 业务接入阶段交互评审时 |
| WB-Q5.1 | 如何选择目标、展示进度、替换结果和恢复旧图 | 页面可选中内容，输入区显示目标名称；生成中保留旧图，成功后替换；失败可局部重试，历史版本提供恢复入口 | 用户能看清改哪一张、保留了什么；需设计选择、处理中、部分失败和历史状态 | 业务接入阶段交互评审时 |
| WB-Q9.1 | 保存恢复和备份体验如何呈现 | 内容自动保存，显示真实保存状态与失败反馈；明确完整备份需包含项目文件和宿主状态 | 用户无需反复手动保存，也能知道恢复边界；备份不是只复制一个目录 | 实例保存反馈在机制阶段评审；产物保存与恢复在业务阶段确定 |
| WB-Q11 | 安装、固定、停用、移除及权限说明如何呈现 | 安装前展示来源和所需能力；添加实例后进入项目导航，固定与停用使用不同操作 | 避免把隐藏入口当成停用或删除，也避免能力声明被误认成授权；增加操作说明和状态设计 | 插件机制阶段交互评审时；完整多实例管理见下表 |
| WB-Q12.1 | 删除实例时是否同时停止运行中的生成 | 删除时一并 Stop，并在确认中列出受影响 Session；保留对话历史和可恢复成果 | 避免继续生成无法写回的结果及后续费用；会中断这些 Session 当前回合，需要明确提示 | 业务生命周期评审时、删除功能实现前 |

#### 后续范围，暂不展开

下表保留推荐答案与原因，不纳入基础插件机制，也不阻塞当前架构设计。进入对应阶段时再设计和评审。

| 编号 | 问题 | 推荐答案 | 原因与主要取舍 | 决策时点 |
|---|---|---|---|---|
| WB-Q7.1 | 本地包导入和实例导出如何操作 | 分成“导出工作台包”和“导出含成果的实例”；导入先校验声明、版本和资源，再创建新实例 | 导出范围清楚，减少误带项目数据；需要额外的状态快照和资源恢复逻辑 | 分享功能设计评审时、实现前 |
| WB-Q8.1 | 预设工作台能否隐藏或重排 | 保留当前可见顺序，隐藏与排序在单独管理功能中设计 | 统一架构不自动增加管理操作；先保留已有使用方式 | 对应管理功能设计评审时 |
| WB-Q12.2 | 可恢复成果保留多久，何时彻底删除 | 首期建议不自动过期，提供显式永久删除并说明影响；清理前检查产物是否仍被引用 | 避免时间到期后意外丢失成果；代价是占用磁盘，需要后续清理入口 | 数据清理方案评审时、删除与清理实现前 |

### 2.3 架构设计与后续业务技术事项

技术工作按插件机制和业务接入分开。架构阶段先明确模块职责、依赖方向、包与实例、页面 SDK、AI 开发说明、生命周期及状态归属，再随实现验证契约。具体接口由技术设计确定；涉及用户行为、费用或数据权限的取舍交产品负责人决定。

用户于 2026-11-10 指定 Codex CLI 与 image2.5 作为验证路径，连接信息使用本地 `.env.local` 中的 `LLM_gateway` 和 `api_key`；随后明确本产品是内部企业工具，先完善功能，不先开展页面安全专项设计。页面容器先服务加载、展示、宿主通信和状态更新，安全专项后置，不作为首期功能接入或验收门槛。上述为对话决定，具体实现随对应阶段评审。

| 阶段 | 技术事项 | 设计要求与确定时点 |
|---|---|---|
| 插件架构 | 模块职责与接缝 | 明确宿主、插件页面、Project、Navigation、Session 与 CLI Adapter 的责任及依赖方向；将具体业务与通用机制分开，架构产出见 §3 |
| 插件架构 | 包格式、SDK、版本与状态 | 围绕声明、页面入口、包与实例、通信、生命周期、恢复和错误反馈设计最小契约；不要求每个包具有图片位置或出图能力；不改变现有 Git 忽略策略 |
| 插件架构 | 页面容器与 AI 创建通道 | 本期采用 iframe 与页面 SDK，AI 读取项目内开发说明并编辑草稿；具体接缝见工作台规格 §9。业务命令桥或 MCP 后续按实际需要选择 |
| 后续业务 | WB-Q6：CLI 与出图工具 | 保留用户指定的 Codex CLI 与 image2.5；在业务接入时检查模型 ID、参考图、文件返回、费用、Stop 和错误反馈，不阻塞插件机制 |
| 后续业务 | 位置、产物与提交 | 保留现有候选方案，业务阶段再确定位置寻址、产物发布、版本、冲突及恢复；本地命令桥是候选传输，不预先定为宿主通用协议 |

先前指定的网关与出图工具配置仅用于后续业务接入，不是插件架构设计或机制验收的前置条件。

## 4. 外部参考：DeepSeek Harness Creator Mode

### 4.1 调研结论与证据边界

调研日期：2026-11-10。依据本日用户“以 AI 创造插件，和我们想的一样”的调研请求补充。本节作为已确认方案的外部参考，不扩大 §2 的阶段范围或兼容承诺。

方向确实一致：用户描述需要的工作方式，AI 编写可由宿主加载的扩展，使用中继续通过对话调整。DeepSeek [官方产品页](https://www.deepseek.com/en/harness/)将 Creator Mode 定位为通过对话扩展工具、技能和界面，并演示创建悬浮番茄钟插件。对我们而言，这为“用户通过 AI 创建专用工作台”提供了具体产品与工程参考。

来源事实集中维护在 [Harness 调研 §3](references/deepseek-harness/README.md#3-来源事实用户通过-creator-创建插件)：包括 Creator 预设、开发 skill 与模板、运行时接口查询、创建草稿入口、安装及验证流程。源码基线为 `fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159`；官方页面另按上述日期核对。本轮未运行 Harness 或实测生成插件，官方演示与 Agent 工作指令均不作为实机验收证据。

### 4.2 对我们方案的启发与差异

以下为 AI 的适配判断，关联已有方向和候选规格；不是对上游功能的新增断言。

| 参考点 | 对 AI Studio 的具体收益 | 对应现有方案与适用边界 |
|---|---|---|
| 把创建插件组织成普通对话中的开发流程 | 用户从工作目标进入，AI 可沿用 Session 的文件操作、错误反馈和迭代能力 | 对应 WB-Q3、WB-Q10；继续复用 CLI Session，无需因上游称为 Mode 就另建 Agent 引擎 |
| 为 AI 提供版本对应的开发说明、模板与可查询的接口 | AI 能依据实际能力生成页面，并根据校验反馈修复，减少猜测宿主 API | 对应 [工作台规格 §4.1](../specs/workbench/spec.md#41-页面-sdk-与-ai-开发说明)；本期以项目内开发说明、Schema 和 SDK 类型覆盖通用包字段与接口；未增加命令桥或 MCP 服务，具体实现见工作台规格 §9 |
| 将生成文件、加载成功和实际可用分开反馈 | 用户能知道卡在包检查、页面加载还是操作执行，AI 能针对具体失败继续修改 | 对应 WB-Q3.1、WB-Q5.1；在后续功能验证中检查导航打开、内容选择、局部更新与重新打开后的状态，单凭文件存在不能判定完成 |
| 页面操作与对话操作共享宿主业务能力 | 减少“按钮改一套状态、AI 改另一套状态”的不一致，便于持续操作生成的工作台 | 对应包、实例和产物绑定方案；先定义通用的宿主通信边界，业务阶段再接入实例内容的读取与提交规则，不扩展为任意宿主能力调用 |
| 将工作台结构编辑与日常内容生成明确分开 | 创建出的页面可以长期使用，出图任务不会顺带改掉布局或位置定义 | 对应 WB-Q4、WB-Q4.1；这是我们的既定方向，不能仅凭上游 Creator 名称推定其具有同样的模式边界 |

最需要保留的差异是预览与生效范围：Harness 的 Creator 指令以当前 profile 中安装的插件作为首次预览；我们暂采纳“草稿预览后添加至 Project”，并区分可复用包和项目内实例。建议沿用我们现有方案，让用户在应用前看清页面及结构变更；代价是宿主需要维护草稿与实例两种状态。上游的 profile 安装机制不能直接承担我们的实例绑定与产物版本管理。

建议借鉴它完整的创建和修正流程，继续建设范围明确的小型工作台宿主。整体引入 Cordis 或兼容 DSH 包会增加模块加载、配置组合及生命周期适配成本；现阶段的五图工作流不需要这些兼容承诺。实现耦合与复用边界见 [Harness 调研 §6](references/deepseek-harness/README.md#6-我们的判断哪些做法值得参考)，沿用 WB-Q10。
