## 1. 需求管理约定

- `P0`：V1 MVP 必须交付。
- `P1`：V1 可延后或在 P0 完成后交付。
- `FR-*` 是功能需求的稳定标识；设计稿、技术方案、开发任务和测试用例应优先引用 FR ID，而不是复制整段需求。

## 2. 核心功能需求

### Project 管理

### FR-PROJ-001 打开本地 Project

**优先级：P0**

用户可以选择本地文件目录并作为一个 Project 打开。

#### 要求

- 一个 Project 必须绑定一个本地目录；
- 同一个 Project 后续可以重新打开；
- Project 应记录其基本 UI 状态；
- 选择的目录已在某个 Tab 中打开时，切换到该 Tab，不重复打开。

#### 验收标准

- 用户可以成功选择合法本地目录；
- 打开后自动创建/恢复对应 Project；
- Main Canvas 可以正常进入该 Project。

---

### FR-PROJ-002 多 Project Tab

**优先级：P0**

顶部使用 Tab 形式展示当前已经打开的多个 Project。

#### 要求

- 支持多个 Project 同时保持打开状态；
- 点击 Tab 切换 Project；
- 支持关闭 Tab；关闭仍有 Running 或 Needs Input Session 的 Tab 前需要用户确认，确认后停止这些 Session 的当前一轮，CLI Conversation 保留，重新打开该 Project 后可继续；
- 关闭 Project / 退出应用时，所有未退出的用户 Terminal 也纳入一次合并确认，列明受影响的 Session 与 Terminal；包括仅停在 Shell 提示符的终端。取消保留资源，清理失败保留诊断和重试入口，不静默宣称已关闭（2026-10-13 确认，DEC-14；FR-TOOL-004）；
- 支持新增 Project；
- 每个 Tab 对应一个独立本地目录；
- 非当前 Project 存在 Needs Input、Error 或 Completed Unread Session 时，其 Tab 显示单个注意力状态点（表现见 UX Specification 第 7 节）。

#### 验收标准

切换 Project 时，各 Project 的：

- Session；
- Project View；
- Context Panel；

不得混淆。

---

### FR-PROJ-003 Project 状态恢复

**优先级：P0**

重新进入 Project 时恢复上一次工作状态。

至少包括：

- 上一次选中的 Project View 或 Session；
- Context Panel 展开状态；
- 当前工具类型。

首次进入 Project：

默认显示 Overview。

---

### 左侧导航

### FR-NAV-001 导航区域划分

**优先级：P0**

左侧导航必须明确划分为两个区域。

上部：

**工作台**

下部：

**Session History**

两个区域之间使用清晰但低视觉噪音的分隔线。

---

### FR-NAV-002 Project View Navigation

默认显示：

1. Overview
2. Progress
3. Architecture
4. Agent Team
5. Business Flow

预设与自定义工作台使用同一导航列表，点击后切换 Main Canvas 至对应工作台。概念依据 [01 Workbench](<01. Product Definition.md#workbench>)，本轮统一决定见 DEC-29。

---

### FR-NAV-003 Session History

**优先级：P0**

Session History 采用类似 ChatGPT 的纵向历史记录形式。

要求：

- 新 Session 自动加入历史记录；
- Session 数量持续增长；
- 列表支持滚动；
- 支持 Session Rename；
- 优先复用 CLI 原生提供的 Session Name；
- 如果 CLI 不提供名称，可由客户端生成名称；
- 按最近一次用户发送消息的时间倒序排列，并按日期分组；Agent 输出不改变排序，避免并行 Session 在列表中跳动。

---

### New Chat

### FR-CHAT-001 创建 Session

**优先级：P0**

用户点击 New Chat 时：

1. Main Canvas 切换到新对话草稿，输入区可立即输入；
2. 使用当前 Project；
3. 使用应用级 Default CLI（已有明确选择的草稿保留其 CLI；启用规则见 FR-CHAT-002）；
4. 用户发送第一条消息时，创建新的 CLI Conversation Session；
5. 新 Session 立即出现在 Session History。

未发送任何消息的草稿不创建 Session，也不进入 Session History，避免产生空 Session。

---

### FR-CHAT-002 CLI 选择

用户可以在创建 Session 时选择：

- Codex CLI；
- Claude Code CLI。

CLI 启用列表与 Default CLI 为应用级设置，所有 Project 共用，不要求逐项目重复设置（2026-10-25 用户对细化方案回复「是这个意思」确认；diff 待审阅）。设置中可启用或取消 CLI；新建对话只列出已启用项，检测只针对已启用项。默认仅从已启用且可用项中选择；取消不影响运行及历史 Session。详细状态、回退和草稿规则由 [CLI 管理规格](../specs/settings/spec.md#cli-管理与默认-cli2026-10-25-确认)负责。

普通 New Chat：

直接使用 Default CLI。

如用户希望使用其他 CLI，应提供扩展入口，例如 New Chat 下拉菜单。

---

### FR-CHAT-003 Session CLI 锁定

Session 创建完成后：

- CLI 类型固定；
- 不允许将 Codex Session 切换成 Claude Code Session；
- 可以使用该 CLI 自身支持的模型切换能力。

---

### Session Conversation

### FR-SESSION-001 Conversation 展示

**优先级：P0**

点击 Session 后进入完整 Conversation Mode。

要求：

- 页面打开后直接显示对话最底部；
- 不从顶部自动滚动到最底部；
- 保持类似 ChatGPT 的阅读体验；
- 输入区固定在对话区域下方。

---

### FR-SESSION-002 Session 连续性

同一 Session 可以持续进行多轮开发工作。

客户端不得将每轮对话人为拆分为：

- Task；
- Run；
- Job。

底层实现允许存在 Invocation、Process 等技术概念，但不得成为主要用户信息架构。

---

### Session 状态与提醒

#### 状态模型

Session 状态的目标是：

**管理用户注意力，而不是进行任务管理。**

---

### FR-STATE-001 Running

当 CLI 正在：

- 思考；
- 输出内容；
- 执行命令；
- 使用工具；
- 修改文件；

Session 显示 Running 状态。

UI 应采用轻量动态状态，例如 Spinner 或动态点。

---

### FR-STATE-002 Needs Input

当 Agent 正在等待：

- 用户输入；
- 用户确认；
- 用户授权；
- 用户选择；

Session 显示 Needs Input。

Needs Input 属于高注意力状态。

用户作出答复（确认、授权、选择或输入回复）后清除 Needs Input；仅打开查看不清除。

---

### FR-STATE-003 Error

CLI 进程或执行过程出现错误时：

Session 显示 Error 状态。

用户点击查看该 Session 后，Session History 中的 Error 提醒清除；错误详情保留在 Conversation 中。用户再次发送消息时，客户端尝试恢复对应 CLI Conversation。

---

### FR-STATE-004 Completed Unread

当 Agent 完成当前一轮工作，而用户当前未查看该 Session 时：

Session History 显示绿色完成提醒。

推荐形式：

**绿色圆点。**

该状态表示：

> 有新的 Agent 工作结果需要用户查看。

不是：

> 整个 Session 已经结束。

Project View 左侧正在显示的 Session 视为用户正在查看，完成时不产生 Completed Unread。

---

### FR-STATE-005 完成提醒清除

当用户点击对应 Session：

- 直接进入 Conversation 最新位置；
- Completed Unread 提醒立即清除。

不增加额外：

- Mark as Read；
- 手动确认；
- 阅读完成按钮。

---

### FR-STATE-006 无活动状态

历史 Session 在以下情况下：

- 未运行；
- 不等待用户；
- 无错误；
- 没有未查看完成结果；

不显示任何状态标识。

UI 中不得显示 Idle。

---

### FR-STATE-007 Conversation 完成标识

一轮 Agent 响应结束后，可以在 Conversation 内显示：

`Worked for 2m 18s · Done`

或同等语义形式。

Done / Completed 仅描述：

**当前这一轮工作已经结束。**

---

### Session 并发

### FR-SESSION-003 多 Session 并行

**优先级：P0**

同一 Project 下多个 Session 可以同时 Running。

例如：

```text
Session A — Codex — Running
Session B — Claude Code — Running
Session C — Codex — Needs Input
```

每个 Session 必须拥有：

- 独立 CLI Conversation；
- 独立运行状态；
- 独立上下文；
- 独立模型配置。

多个 Session 可以共享同一个 Project Directory。

V1 不提供自动 Worktree / Branch 隔离；共享目录的写入协调与冲突检测边界遵循 [01 第 4 节](<01. Product Definition.md#4-v1-非目标范围>)。Session 并行与 Runtime 隔离不意味着文件系统隔离或防覆盖保证（2026-10-11 确认；DEC-11）。

---

### 输入区

### FR-INPUT-001 基本结构

输入区包含：

- 文本输入；
- Context / Attachment 入口；
- Model Selector；
- Send / Stop 控件；
- 后续 CLI 支持的其他必要控制。

依据 [01 第 8 节原则 24](<01. Product Definition.md#8-已确认的产品原则>)，Running 期间支持所用 CLI 原生允许的输入；当前回合追加与后续回合排队保留各自语义，不能统一禁发。其他原生控制的接入缺口同样作为待实现项跟踪，不能以本切片未实现缩减产品要求。输入接收、回合归属及 Stop 对排队消息的处理须依据原生行为验证（2026-10-11 确认；diff 待审阅）。

---

### FR-INPUT-002 Model Selector

Model Selector 必须放置在输入区内部。

不在顶部 Project Tab Bar 设置全局 Model Selector。

Model Selector 展示当前 Session 所使用 CLI 支持的模型。

---

### Project View

### FR-VIEW-001 默认 Project Views

**优先级：P0**

系统默认提供：

| View | 主要解决的问题 |
|---|---|
| Overview | 当前项目整体情况如何 |
| Progress | 项目目前开发到哪里 |
| Architecture | 系统由哪些模块组成、如何关联 |
| Agent Team | 当前项目使用哪些 Agent，各自负责什么 |
| Business Flow | 业务流程如何运作，并如何映射到代码 |

---

### FR-VIEW-002 Project View 可扩展

**优先级：P1**

默认五个 View 不是固定上限。

用户可以通过 AI 创建新的 View，例如：

- Database Schema；
- API；
- Deployment；
- Design System；
- Security；
- Requirements。

新增扩展采用工作台包与 Project 内实例，进入当前项目导航。包可包含自定义 Web 页面与结构化定义，声明式组件用于模板；创建、内容写回和生命周期见 FR-WB-001～008 候选需求（方向于 2026-11-10 接受，2026-11-11 调整为插件架构先行，细节待分阶段设计，DEC-28）。预设与自定义工作台采用同一 manifest、HTML、CSS、JavaScript 网页包格式，使用相同加载与 SDK 通道，保留现有内容能力和稳定 ID；概念与决定见 [01 Workbench](<01. Product Definition.md#workbench>) 和 DEC-29。

---

### FR-VIEW-003 View 内容动态生成

本节描述默认五个 View；工作台内容生成与结构编辑的区分见 FR-WB-001、FR-WB-004。

Project View 不采用完全固定的传统 Dashboard 模板。

Agent 可以根据项目实际情况：

- 调整布局；
- 添加节点；
- 添加关系图；
- 添加表格；
- 添加图表；
- 修改内容结构；
- 修改视觉呈现。

Project Knowledge 尚未生成时，不自动启动生成；Preview 显示空状态并提供生成入口，由用户在普通 CLI Session 中发送生成请求。

---

### FR-VIEW-004 数据与展示分离

Project View 不能仅依赖 HTML 作为项目知识数据源。

逻辑结构应满足：

```text
Project Knowledge
↓
Structured Data
↓
Rendering
↓
Generated Project View
```

修改事实信息时更新数据。

修改视觉表达时更新 View。

### 设置与外观

本组需求依据用户 2026-10-12 对话确认新增（[DEC-12](<07. Decisions.md#dec-12-外观主题与设置>)）；本次 diff 待审阅。详细行为见 [settings spec](../specs/settings/spec.md)。

### FR-SET-001 设置入口

**优先级：P0**（2026-10-12 确认）

用户可以从以下入口打开设置：

- 左侧导航左下角的“设置”入口（参考 ChatGPT Desktop）；
- 菜单栏“设置…”；
- 快捷键 ⌘,。

设置在应用内以对话框呈现：左侧为分类，右侧为该分类的内容。V1 提供“外观”和“CLI”；CLI 管理分组与固定右上检测入口见 [settings spec](../specs/settings/spec.md#cli-管理与默认-cli2026-10-25-确认)（2026-10-25 确认）。

---

### FR-SET-002 外观主题

**优先级：P0**（2026-10-12 确认）

外观由颜色模式与主题组合而成：

| 模式 | 说明 |
|---|---|
| 跟随系统（默认） | 随 macOS 的浅色 / 深色设置切换，系统切换后应用立即跟随 |
| 浅色 / 深色 | 固定为该模式，不随系统变化 |

| 主题 | 呈现 | 来源 |
|---|---|---|
| 毛玻璃 | 整个窗口为同一种毛玻璃，透出并模糊窗口后方的桌面；Conversation、右侧区域等内容区是叠在上面的磨砂层 | 交互原型 v04 |
| 纯色 | 不透明背景与中性色：浅色模式下为白色背景，深色模式下为深灰背景；只在系统开启“降低透明度”时自动使用 | 交互原型 v03（浅色）；名称与深色取值已按 SET-Q6 / SET-Q7 确认（DEC-20） |

颜色模式依据 2026-10-12 对话“默认跟随系统设置，也可以支持3种模式的选择”，作用于整个应用，包括原生菜单、对话框与窗口材质。主题不由用户选择：依据用户 2026-11-12 要求，设置不再提供“纯色”选项，纯色只作无障碍回退；旧版本保存的纯色偏好按毛玻璃处理（DEC-31）。

- 点选模式或背景颜色后整个窗口立即切换，不需要重启或二次确认；切换不改变 Project、Session、草稿与布局状态。
- 模式与背景颜色为应用级偏好，重启后保持。
- 毛玻璃内容层的浓淡固定，不提供调节。
- 毛玻璃可选择背景颜色：极光（默认）、薄荷、晚霞、海雾，或“无”（只透出窗口后方的桌面）；深色模式下为同色相的深色渐变；切换立即生效，应用级保存，系统改用纯色外观时保留该选择（2026-10-12 用户要求“毛玻璃目前没有背景颜色，也支持选择多种背景颜色的选择”；色板 2026-10-12 确认，见 settings spec SET-Q5）。
- 系统开启“降低透明度”时显示为纯色外观，设置中注明原因；系统选项关闭后自动恢复毛玻璃。

## 3. 默认 Project View 定义

### Overview

#### 目标

帮助用户在重新进入项目时快速恢复上下文。

#### 建议内容

包括但不限于：

- Project Summary；
- Overall Progress；
- Current Focus；
- 核心技术栈；
- Architecture Summary；
- Agent Summary；
- Recent Sessions；
- Needs Input；
- Recently Completed。

Overview 保持轻量，不设计为复杂 Dashboard。

---

### Progress

#### 目标

表达：

**项目目前做到什么阶段。**

#### 要求

不采用传统 Jira 模型作为主要表现方式。

避免强制：

- Sprint；
- Epic；
- Story；
- Ticket。

Project Progress 可以根据：

- Git；
- Session；
- 项目源码；
- TODO；
- 用户对话；
- Project Knowledge；

由用户通过普通 CLI Session 请求 Agent 整理。客户端不在后台自行分析进度或发起隐式模型调用；生成触发遵循 FR-VIEW-003，读取、校验和 Preview 刷新遵循 DEC-07（2026-10-11 确认；DEC-11）。

---

### Architecture

#### 目标

表达系统语义架构，而非文件目录。

包括：

- 模块；
- 服务；
- 技术栈；
- 数据流；
- 外部服务；
- 模块依赖；
- Component / Service Relationship。

Files Tree 不属于 Architecture View 的替代品。

---

### Agent Team

#### 目标

直观呈现项目当前使用的 Agent 及其职责。

#### V1 原则

客户端不定义自己的 Agent Profile 标准。

只展示和利用底层 CLI 已经支持的能力，例如：

- Codex Agent；
- Claude Code Agent；
- Agent 配置；
- Skill；
- Rule；
- Instructions。

如何配置、调用哪些 Agent，由用户和底层 CLI 决定。

---

### Business Flow

#### 目标

表达产品的业务逻辑，并建立业务与代码之间的映射。

示例：

```text
User Registration
↓
Email Verification
↓
Onboarding
↓
Create Project
↓
Subscribe
```

单节点可以进一步关联：

- Trigger；
- Frontend；
- API；
- Service；
- Data；
- Result。

## 4. Project View 工作模式

以下为默认 View 的基线；工作台复用普通 Session，逐次上下文与页面交互按第 9 节处理。

### FR-VIEW-005 左右布局

进入 Project View 时，Main Canvas 必须采用左右布局：

左侧：

**Conversation**

右侧：

**Project View Preview**

结构如下：

```text
┌──────────────────────┬──────────────────────────┐
│                      │                          │
│    Conversation      │      View Preview        │
│                      │                          │
│                      │                          │
│                      │                          │
│ ┌──────────────────┐ │                          │
│ │ Input            │ │                          │
│ │ Model          ↑ │ │                          │
│ └──────────────────┘ │                          │
└──────────────────────┴──────────────────────────┘
```

设计目的：

- 保证 Conversation 有完整纵向空间；
- 保证 Project View 有足够二维展示空间；
- 用户可以一边描述修改需求，一边观察 View 更新。

---

### FR-VIEW-006 Project View Conversation

Project View 左侧对话：

**本质仍然是普通 CLI Session。**

不得创建：

- 特殊 Project Chat；
- 唯一 Project Session；
- 独立的隐藏聊天系统。

---

### FR-VIEW-007 Project View New Chat

用户从 Project View 中创建 New Chat 时：

1. 与 FR-CHAT-001 相同，先进入草稿，用户发送第一条消息时创建新的普通 CLI Session；
2. 自动引用当前 Project；
3. 自动将当前 Project View 作为相关上下文；
4. 可以根据用户选择使用 CLI 原生 Skill / Agent / Instructions；
5. 新 Session 必须同步出现在左侧 Session History。

进入 Project View 本身不创建 Session。Session 记录其创建时所在的 Project View，用于在该 View 中列出相关对话。

---

### FR-VIEW-008 不绑定长期 Session

一个 Project View 不永久绑定唯一 Session。

Architecture 可以存在多个独立 Session，例如：

- 架构整体讨论；
- 支付架构重构；
- AI 模块设计。

避免长期 Session Context 持续膨胀。

## 5. Context Panel 与工程工具

### Context Panel

#### 基本要求

右侧提供可折叠 Context Panel。

V1 包含五个入口（Search 于 2026-10-26 确认纳入，DEC-25）：

1. Files
2. Search
3. Diff
4. Browser
5. Terminal

---

#### 操作原则

Context Panel 完全由用户主动控制。

AI 不应因为执行某项任务而自动：

- 弹出 Diff；

### FR-TOOL-001 Files Explorer

提供当前 Project 的本地文件目录浏览。

要求：

- 展示目录层级；
- 展开/折叠目录；
- 选择文件；
- 支持将文件作为当前 Session Context。

Files 不作为主界面长期核心区域。

文件查看采用按需加载；目录按展开需要读取，文件变化刷新时保留仍有效的展开与选择状态。查看文件不自动添加上下文（2026-10-12 确认，DEC-10）；实现细节见 [工具规格](../specs/tools/spec.md#fr-tool-001-files)。

文件上下文交付须贯通 Files、Input、Session 与 Adapter，并分别验证两种 CLI 实际收到文件引用；覆盖普通发送及原生支持的运行中追加 / 排队，不能只显示标签或静默丢弃引用（2026-10-13 确认，DEC-14）。优先传递经主进程校验的文件引用，具体契约见工具规格 §4.1。

对齐 VS Code 资源管理器的基本操作（2026-10-26 确认，DEC-25）：

- 右键菜单：新建文件 / 文件夹、重命名、删除（移到废纸篓）、复制 / 剪切 / 粘贴、复制路径 / 相对路径、在 Finder 中显示、在终端中打开、在文件夹中查找、用 VS Code 或默认应用打开、添加到对话；支持多选与拖拽移动。
- ⌘P 快速打开：按文件名与路径模糊匹配，遵守 .gitignore。
- 树中按 Git 状态着色并标注字母，被忽略项变灰；按文件类型显示图标；可全部折叠。
- 查看器保持只读：支持查找、跳转到行、代码折叠、自动换行，以及 Markdown / 图片预览。修改文件内容通过 Agent 或“用 VS Code / 默认应用打开”完成，应用内不提供编辑保存（2026-10-26 确认）。

### FR-TOOL-002 Diff Viewer

用于审核 Agent 对项目产生的文件修改。

至少应支持：

- Modified；
- Added；
- Deleted；
- 单文件 Diff；
- 多文件变更列表。

V1 提供两种明确区分的只读范围（2026-10-10 确认；取舍见 [DEC-08](<07. Decisions.md#dec-08-diff-范围与原生轮次变更>)）：

- **项目变更（Project Diff）**：当前 Project 目录相对 Git HEAD 的全部未提交变更（含未跟踪文件），不按 Session 归因；多个 Session 共享同一目录时，不将仓库变化归属于某个 Session。
- **本轮变更**：展示 CLI 原生记录的该轮文件和补丁。Conversation 完成行可显示该记录中的文件数；用户点击后打开该轮 Diff，并定位到对应文件。记录随轮次保存，后续工作区变化不改写已保存的补丁；记录的覆盖范围不得被解释为所有命令产生的完整修改。
- CLI 无法提供本轮变更时，显示“本轮变更不可用”，提供“查看项目变更”入口；不以 Project Diff 冒充本轮 Diff，不把未知数量显示为 0。
- 只有原生补丁而没有对应历史完整文件时，展示保存的补丁；不能将当前工作区内容作为历史原文。历史数据与显示方式的边界于 2026-10-12 确认，见 DEC-10。
- 非 Git 目录的 Project Diff 显示说明性空状态和 Git 初始化指引；客户端不自动初始化 Git，不自建隐藏仓库或项目级快照基线。原生轮次补丁能否在非 Git 目录独立展示，按 04 第 1 节第 13 项单独验证。

MVP 不提供 Staged / Unstaged 分组与 Stage、Unstage、Commit、Discard 等 Git 操作界面；已暂存、未暂存内容按相对 HEAD 的最终差异统一展示，Git 操作通过用户 Terminal 或 Agent 完成（2026-10-10 确认；2026-10-26 再次确认保持只读）。

查看控制对齐 VS Code 的对比编辑器（2026-10-26 确认，DEC-25）：文件列表可切换列表 / 树视图；单文件 Diff 可切换并排 / 行内、跳到上一处 / 下一处变更、折叠未改动区域，并可在 Files 中打开该文件。

### FR-TOOL-003 Browser Preview

用于预览本地 Web 项目。

主要场景：

- 查看 localhost；
- 验证 Agent UI 修改；
- Web 开发辅助；
- 与 Conversation 配合检查页面。

页面使用与主应用分离的渲染上下文，不获得应用 IPC 或本地文件 / Shell 权限（2026-10-12 确认，DEC-10）。地址、实例与显示状态按 Project 管理。

首轮交付 localhost / 回环地址预览；一般外站内嵌与客户端新增的 Agent 页面自动化另行评估。外站跳转提示用户选择是否用系统浏览器打开，不自动打开。每个 Project 使用独立浏览器分区，首轮默认不跨应用重启保存登录数据，上次地址仍保存；可选持久化后续评估。内嵌 OAuth 登录及跨站预览不列入首轮交付承诺；原生 CLI 能力接入要求不变（2026-10-13 确认，DEC-14；[工具规格 TOOLS-Q1、Q5、Q6](../specs/tools/spec.md#12-已确认原则)）。上述导航范围与登录数据边界已由下段取代。

对齐 VS Code 内置浏览器（2026-10-26 确认，DEC-25）：

- 可打开任意 http / https 网址；地址栏无需输入协议，本地与内网地址补 `http://`，其他补 `https://`。其他协议仍提示用户选择是否交给系统应用。
- 提供后退、前进、刷新、停止、DevTools、用系统浏览器打开、页面缩放；下载前询问保存位置。
- 浏览数据（Cookie、登录、缓存）由所有 Project 共享并跨重启保存，可在 Browser 菜单中清除；客户端新增的 Agent 页面自动化仍另行评估。
- 第 3 步补充多个 Browser Tab、历史与收藏，以及按网站询问摄像头 / 麦克风 / 定位等权限；上线前权限保持默认拒绝。

### FR-TOOL-004 User Terminal

V1 集成系统 Terminal。

默认工作目录：

**当前 Project Directory。**

用户可以执行：

- npm；
- pnpm；
- git；
- python；
- shell command；
- 项目自身脚本。

V1 在每个 Project 内支持轻量多实例 Terminal Tabs（2026-10-10 确认；取舍见 [DEC-09](<07. Decisions.md#dec-09-project-内的-terminal-tabs>)）：

- 首次打开只创建一个终端，用户可新建、切换和关闭 Tab；MVP 不做终端分屏或复杂布局。
- Terminal 属于 Project；切换 Session、工具或 Project，以及隐藏面板时，保留终端进程和输出。
- 每个实例使用独立 PTY，与 Agent Runtime 隔离；Session 的 Stop 不影响用户 Terminal。
- 用户可在一个终端运行开发服务器，在另一个终端执行测试或 Git 命令。

Project 关闭 / 应用退出时的合并确认与失败反馈遵循 FR-PROJ-002；Session Stop 仍不得影响用户 Terminal。隐藏面板、关闭窗口但未退出应用与结束终端实例须区分（2026-10-13 确认，DEC-14）。

对齐 VS Code 集成终端（2026-10-26 确认，DEC-25）：⌘+点击链接打开（本地网址进入内置 Browser，其他网址交给系统浏览器，`文件:行号` 在 Files 定位）；⌘F 查找、⌘K 清屏；右键菜单（复制、粘贴、全选、清屏、重命名、关闭）；Tab 可重命名并显示前台进程名；从 Files 拖入文件插入路径。第 3 步提供分屏（⌘\），取代上文“MVP 不做终端分屏”。

### FR-TOOL-005 Search

对齐 VS Code 的全文搜索（2026-10-26 确认纳入，DEC-25）：

- ⌘⇧F 或右侧工具栏打开；在当前 Project 内搜索文本或正则，可切换大小写、整词，设置包含 / 排除规则。
- 默认遵守 .gitignore 并跳过 `.git`；结果按文件分组显示匹配行与数量，点击在 Files 中打开并定位到行。
- 结果数量与耗时有上限，超出时明确提示；不提供替换（与“应用内不编辑”一致）。
- 实现使用 ripgrep（与 VS Code 相同）；Files 右键“在文件夹中查找”预填范围。

### FR-TODO-001 任务记录与来源

用户可以把手动输入、Conversation / Project View 消息、授权的 Agent 请求、自动化或仓库 Issue / PR 转成 To-do。复用完整 Composer（附件、文件 / Skill 引用、原生 Agent 选项）；保存目标 Project、来源、任务描述与实际执行配置。普通 Session 保持可独立使用。

### FR-TODO-002 任务状态与生命周期

任务生命周期独立于 Session 回合；区分待办、排队、准备、执行、等待输入、待审阅、交付与终结。Agent 回合结束或自报成功不等于验收 / 合入完成。失败、取消可恢复并保留执行历史；延后和归档是可见性标记，不冒充 Done。Done 必须有审阅后的交付或用户明确完成记录，不能只依赖 Agent 文本。

### FR-TODO-003 跨 Project 总收件箱

提供应用级总收件箱、全部任务看板 / 列表和 Project 内快捷视图；支持搜索、筛选、数量提示、延后及归档。总收件箱聚合跨 Project 的 To-do 待答复、待审阅、失败，并建议纳入普通 Session 的 Needs Input、Error、Completed Unread；同一个任务及其 Session 的注意力事件去重。任务详情可跳转到正确的 Project、Session、Diff / PR；查看通知不等于接受交付。已关闭 Tab 的 Project 仍可被发现，不能为显示收件箱偷偷启动 Agent。

提供独立 Worktree / Branch、明确的 base branch / revision、初始化命令与可取消准备过程。隔离执行必须先于写入任务的并发或无人值守运行交付；基线、复用、恢复和清理均可追踪。Worktree 隔离 checkout，不等于操作系统沙箱，不承诺隔离数据库、端口、网络与凭据等共享资源。

Review 集中展示结果、里程碑、运行配置、任务级 Diff、检查结果、用量（CLI 可提供时）与问题。支持检查、要求修改、继续、提问、无变更完成、放弃及延后。Preflight、审阅、交付和清理分别记录；没有执行检查不能展示绿色通过。Merge / PR 的审阅与交付语义见 FR-TODO-008。

提供人工触发合入、合并队列、冲突处理、Squash / 保留历史策略，以及显式开启的自动合入；落地以 Git 事实验证，不由 Agent 自报决定。支持 GitHub、GitLab、Gitea / Forgejo 的 Issue / PR 转任务、规则扫描 / webhook、创建和更新 PR / MR、回写来源及状态。外部来源内容不是执行 / 推送 / 合并授权；PR 已提交、已合并、任务已完成分别呈现，不把交付 PR 误报为合并。

### FR-TODO-009 设置、模板与清理

支持全局默认 / Project 覆盖 / 单任务配置、可复用任务模板、分阶段附加指令、初始化 / preflight、Worktree 位置、合入 / 清理偏好及原生支持下的恢复前压缩。提供搜索、看板 / 列表、拖拽、延后、归档 / 恢复、删除和独立清理入口。任务、会话、分支、Worktree 的删除影响必须分开显示；存在未保存或未交付工作时不能静默清理。

支持位置写回的业务插件，其页面与 AI 共用稳定位置 ID、类型和约束。页面顺序变化不改变已发送请求的目标；定义的机器约束与风格等质量目标分别判断。验收：AC-WB-02、AC-WB-03。

### FR-WB-003 普通 Session 与逐次上下文

复用普通 CLI Session，每次发送读取当前实例、定义、位置版本、用户选择和可用能力。上下文可见、可移除；移除后本轮作为普通对话，不自动写回工作台。不创建隐藏会话。验收：AC-WB-03。

### FR-WB-004 真实产物与宿主提交

AI 通过已授权能力产生本地文件，宿主校验归属、目标范围与文件后导入并提交绑定。逐项成功结果直接显示并保留旧版，不以 AI 完成声明代替产物，不以文件校验代替作品质量验收。验收：AC-WB-03、AC-WB-04。

### FR-WB-005 失败、并发与恢复

保留已成功结果和失败前内容；提交重试复用文件并按操作 ID 幂等处理。旧版本结果不得静默覆盖当前位置。Stop 撤销后续发布权限，重启恢复已提交状态，不自动重新生成。验收：AC-WB-04、AC-WB-05、AC-WB-06、AC-WB-08。

### FR-WB-006 包、实例与生命周期

包与 Project 内实例分离，由宿主提供导航。安装、添加、取消固定、停用、删除和包卸载分别处理；页面卸载与 Session Stop 分开。停用保留已授权执行；删除只对已移除的自定义实例提供，先停止从该实例及其编辑草稿发起的运行中 Session，再删除实例与保存的数据，会话历史与项目文件保留。基础列表管理按用户 2026-11-11 确认纳入本轮：添加、重命名、项目内排序、移除恢复及草稿删除；实例永久删除于 2026-11-12 确认。详细规则见[工作台规格 §9.8](../specs/workbench/spec.md#98-fr-wb-001006008-工作台列表管理)；移除保留文件、会话和状态，包卸载与文件彻底清理继续后置。验收：AC-WB-01、AC-WB-07、AC-WB-08；列表管理补充场景见 05 §6.1。

### FR-WB-007 保存、改版与分享

包文件与实例产物保存在本地，宿主数据库管理实例、绑定、历史和执行记录。明确项目文件与宿主状态的备份依赖；编辑保留稳定位置绑定，包升级由用户选择。后续分享时，包默认不带成果，带成果分享通过实例导出恢复状态与资源，不携带对话或凭据。分阶段验收：AC-WB-02、AC-WB-06；分享阶段另补导入导出验收。

### FR-WB-008 页面隔离与能力边界

按 [09 §2.3](<09. Workbench Discussion.md#23-架构设计与后续业务技术事项>)的内部企业工具功能优先决定，首期完善页面加载、展示、宿主通信、当前实例状态更新及卸载恢复；页面加载失败可重试，对话与已保存成果保留。页面隔离与安全专项设计后置至功能完善后，不作为首期接入或验收门槛。首期功能验收：AC-WB-08；后续安全专项：AC-WB-07。
