## 1. 结论与开发准入

可以启动 macOS 应用骨架和 CLI Adapter 开发。真实模型调用已经证明：两个 CLI 可以创建独立 Session、流式回复、恢复原 Session、等待宿主授权 / 选择，并在取消和进程异常退出后继续对话。

**Codex 原生 Stop 的进程清理路径已验证，产品 Stop 尚未端到端验收。** 本机 Codex 0.161.0 在工具执行中收到 `turn/interrupt` 后返回 `interrupted`，但测试 Python 子进程在 5 秒后仍然存活。该行为复现 3 次，包括延迟 1 秒、确认子进程启动后再取消的复核；原始证据和失败断言保留。

补充核对官方文档与相同版本源码后，确认 `turn/interrupt` 中断回合时会保留 Unified Exec 后台命令，进程终止有独立原生接口。真实调用已验证：`thread/backgroundTerminals/clean` 可清理目标 Thread 命令，`thread/backgroundTerminals/terminate` 可终止指定命令；系统测试进程退出，同一 Runtime 中另一 Thread 的执行不受影响，两条原 Thread 均保留上下文并可继续对话。正常 Stop 应优先复用这些接口，不能仅凭先前三次观察认定 Codex 进程终止缺陷。

先前已验证的“停止独立 Runtime → 子进程退出 → 新 Runtime 恢复同一 `thread.id`”路径保留为清理失败或接口不可用时的兜底。正式 Adapter 仍须补齐本轮命令归属、清理完成判定、实验接口兼容和兜底隔离校验。

这里是 Runtime / 协议校验结论，不代表 AC-01～AC-07 或完整 P0 已验收。

## 3. 集成接口

### Codex

- 接口：本机 `codex app-server --listen stdio://`，换行分隔 JSON-RPC 消息。
- 创建 / 恢复时保存 `thread.id`，首条回复后跨进程恢复验证保持相同 ID 和上下文。
- 同一 App Server 能并发执行两个 Thread；原生进程清理的 Thread 隔离也已验证。首阶段仍建议每个活动 Session 使用独立 Runtime，以隔离崩溃和 Runtime 终止兜底；正常 Stop 不需要每次重启 Runtime。
- `thread/backgroundTerminals/list`、`clean`、`terminate` 均为实验接口，须开启 `capabilities.experimentalApi: true`；`terminate` 使用 App Server `processId`，不能把该编号当作系统 PID。
- 权限请求是服务端发起的 RPC，必须保存请求 ID 并答复；不能把它当成普通日志文本。
- 主动提问验证使用 Plan 模式的 `item/tool/requestUserInput`；默认模式能否产生该问题未验证。
- 本机 CLI 已生成 445 份实验协议 JSON Schema，供实验校验。正式工程应生成并锁定所支持版本的类型定义，不以网页示例代替本机协议检查。

接口生命周期和授权格式参考 [Codex App Server 官方文档](https://learn.chatgpt.com/docs/app-server)。本次实测沿用用户已安装 CLI 的认证，无新增客户端登录流程。

### Claude Code

- 接口：官方 TypeScript Agent SDK 的 Streaming Input，通过 `pathToClaudeCodeExecutable` 驱动本机 CLI。
- 输入为异步消息流；使用 `includePartialMessages` 接收流式片段，通过 `resume` 恢复原 `session_id`。
- 权限与 `AskUserQuestion` 通过 `canUseTool` 交给宿主等待和答复。
- `system/init` 在本次实测中需要首条消息或控制请求触发；仅创建 Query 后等待该事件可能一直没有响应。
- 校验关闭用户 / 项目配置来源，限定可用工具；未来产品复用原生 Rule、Skill、Context 时需要明确配置加载边界。

这种持续进程接口适合双向对话和取消，见 [Streaming Input 官方文档](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode)；权限与选择回调见 [Handle approvals and user input](https://code.claude.com/docs/en/agent-sdk/user-input)。

### 源码核对与原生 Stop 复核

参考范围：官方 [Open Source 清单](https://learn.chatgpt.com/docs/open-source)确认 Codex CLI、SDK 和 App Server 开源；本次未找到 ChatGPT Desktop 整个客户端开源的官方证据。以下结论针对 Codex 的公开 Runtime / 协议实现，不推断 Desktop Stop 按钮是否有额外处理逻辑。

源码固定为官方仓库 `openai/codex` 的 `rust-v0.161.0`，commit `979011409de0a60b52f179721948e65531d26144`，与本机 CLI 版本一致：

| 核对位置 | 结论 |
|---|---|
| [Unified Exec Process Manager](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/core/src/unified_exec/process_manager.rs#L596) | 在首次等待前保存命令进程，明确保留被中断回合中的后台进程 |
| [CLI `/stop` 分派](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/tui/src/chatwidget/slash_dispatch.rs#L592) | `/stop` 进入后台命令清理路径，与回合中断分开 |
| [App Server 后台命令接口](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/app-server/src/request_processors/thread_processor.rs#L2387) | `clean` 按 Thread 提交清理操作；`terminate` 按内部 `processId` 终止指定命令 |
| [macOS 进程组终止](https://github.com/openai/codex/blob/979011409de0a60b52f179721948e65531d26144/codex-rs/utils/pty/src/process_group.rs#L275) | 底层对工具进程组发送 `SIGKILL`；组信号权限被拒绝时尝试逐个成员发送 |

接口定义见官方 [Clean background terminals](https://learn.chatgpt.com/docs/app-server#clean-background-terminals)。复核开启实验接口，在同一 App Server 内使用两条 Thread，各运行一条带唯一标记、睡眠 120 秒的 Python 命令；没有业务文件输入或文件修改。

| 复核项目 | 实测结果 |
|---|---|
| 第一条 Thread 中断回合 | 收到 `interrupted`；系统测试进程仍存活，原生后台列表有对应命令 |
| 清理第一条 Thread | `clean` 返回 `{}`；系统测试进程退出，后台列表为空；本次观察耗时 51ms |
| 清理时第二条 Thread | 仍处于 `active`，其系统测试进程继续存活 |
| 终止第二条 Thread 的指定命令 | 中断回合后调用 `terminate`，返回 `terminated: true`；系统测试进程退出，后台列表为空；本次观察耗时 48ms |
| 清理后继续对话 | 两条原 Thread 均成功回忆先前标记；App Server PID 未改变，未重启 Runtime |

51ms / 48ms 是单次请求至系统探测确认退出的观察值，不是延迟保证。首轮脚本的进程匹配过宽且审批未匹配归一化命令，误判启动后收到 `no active turn to interrupt`；修正后才完成上述检查。保留首轮事件与结果，不将其计为 CLI 清理故障。

覆盖边界：本次使用单层睡眠进程，验证的是原生接口与同 Runtime Thread 隔离；未验证多层 / 脱离进程组的后代、MCP 服务自身启动的进程、本轮归属映射、同 Thread 先前服务保留、清理失败注入或 GUI Stop。后台列表为空不能单独证明进程退出，本次还使用唯一标记匹配系统 Python 进程并断言退出。

## 5. 状态映射与 Adapter 约束

以下是依据实测的实现建议，不新增 UI 中的 Run / Task 概念。

| 统一事件 / 状态 | Codex 原生来源 | Claude 原生来源 | 客户端规则 |
|---|---|---|---|
| Running | `turn/started` | 宿主发起消息；后续 stream / tool 事件 | 首次提交后及时进入 Running，不能等首个文本片段 |
| 文本追加 | `item/agentMessage/delta` | `stream_event` 的 `text_delta` | 区分增量与完整 assistant 消息，避免重复正文 |
| Needs Input | `item/commandExecution/requestApproval`、`item/tool/requestUserInput` 等 | `canUseTool`（权限或 AskUserQuestion） | 持有请求 ID / tool ID，答复后解除；仅查看不解除 |
| 正常完成 | `turn/completed` 且 status 为 `completed` | `result` 的 success 且 `is_error=false` | 只有成功终态才按当前是否查看产生 Completed Unread |
| 主动取消 | status 为 `interrupted`，另由原生接口清理目标命令 | 本次返回 `error_during_execution`、`is_error=true` | 关联 Stop 请求与回合终态，确认目标资源退出后完成 Stop；不能依赖错误文案判断 |
| 执行错误 | failed / error；进程退出 | error result / SDK 异常 / 进程退出 | 排除已关联的主动取消后显示 Error；保留原生诊断 |

- Stop 的完成条件要包括资源清理；不能收到 `interrupted` 就假定命令已停止。
- Codex 正常 Stop 推荐顺序：暂停当前 Session 的新任务提交 → `turn/interrupt` → 原生目标命令终止 → 确认退出 → 继续使用原 Session；清理失败或接口不可用时再进入独立 Runtime 终止与原 ID 恢复兜底。
- 本轮 Stop 应关联 `turnId` / `itemId` 与 `processId`，通过 `terminate` 精确清理。`clean` 会停止该 Thread 全部后台命令，包括先前启动的服务，只能用于范围明确的整条 Thread 清理；本轮映射及服务保留尚未验证。
- `clean` 的 `{}` 是操作提交回执，不是系统进程退出证明；原生列表清空与 `terminated: true` 也不能代替实际退出确认。须处理清理超时、失败、重复 Stop 和事件竞态。
- Runtime 兜底可能停止同一 Session 先前启动的后台命令；采用共享 Runtime 时不能整体终止进程来兜底一个 Session。任何 Stop 都不得影响其他 Session 或用户 Terminal（FR-SESSION-003；Technical Requirements 第 4 节）。
- Claude interrupt receipt 包含 `still_queued`；本次为空，未验证有排队消息时的 Stop 策略。
- 原生 `idle` 不直接映射为列表文字；按 FR-STATE-006，无活动历史不显示状态。
- UI 未读标记、查看行为和 Error 提醒清除由客户端管理，CLI 不能代替这些状态。
- 每个 App Session 固定 Provider，保存原生会话 ID；恢复不应静默创建新的原生 Session。
- 分离可执行文件发现、登录状态、模型目录和真实调用能力；登录成功并不保证下一轮调用可用。
